半年前我在这台笔记本上搭了一套论文研究用的工作流：LiteLLM 聚合一堆免费模型当网关，Dify 用 Docker Compose 跑起来做工作流编排，再接 Zotero 和一个自己写的监控面板。

现在要把它卸掉。原因很简单：我自己后来写的那套 Agent 工具链，把 Dify 那部分能力覆盖了。留着它，就是留着 1GB 源码、数 GB 镜像，还有每次开机 Docker 要拉起来的十几个容器。

我原本以为这是个十分钟的活。最后花掉的时间，九成在删之前。

## 先别删：把"相关文件"列全

第一反应是 `docker compose down` 然后删目录。但真要动手时发现，我并不知道它到底在哪些地方留了东西。

于是先做了一件事：把跟它相关的东西全部列出来，只列不删。

<DiagramDecommission />

列完之后是这样：

| 位置 | 内容 | 体积 |
| --- | --- | --- |
| 源码目录 | 克隆下来的完整仓库，含 `.git` | 1.03 GB（`.git` 占 413 MB） |
| 数据卷 | 数据库、向量库、插件、上传文件 | 约 600 MB |
| Docker 侧 | 容器、5 个专属镜像 + 5 个通用镜像 | 数 GB |
| 工作目录根下 | 一堆启动、修复、同步脚本 | 几十 KB |

同时冒出来一个我完全忘了的东西：一个**同名的嵌套目录**，466 MB，里面是第二份完整的源码仓库。

::: warning 嵌套副本是整理目录时最容易留下的东西
早期手工搬目录，把工作目录整个复制进了它自己的子目录里，当时没察觉。这种副本不会自己消失，只会在你删东西的时候忽然出现，让你不确定删的是哪一份。
:::

## 分清：哪些能重建，哪些不能

列完清单，我按一个问题给每一项归类——**这东西删了之后，我能不能再造出来？**

能重建的，重点是不心疼：

1. **源码**：开源项目，随时重新克隆。而且我已经决定不用了。
2. **向量库索引**（265 MB）：只要有原始文档，重新索引一遍就有。
3. **插件二进制**（126 MB）：重新装。
4. **镜像缓存**：重新拉。

不能重建的，一共两样：

1. **上传的原始文件**：传进去的东西，删了就真没了。
2. **数据库**（236 MB）：应用定义、知识库元数据、对话历史。工作流还能从导出的 DSL 文件重建，**对话历史没有任何地方备份过**。

::: tip 判断标准只有一条
不是"这个文件重不重要"，而是"这个东西删了之后我还能不能造出来"。前一问会犹豫，后一问立刻就有答案。
:::

## 最意外的一步：54 个上传文件，去重后只剩 16 篇

知识库的上传目录里躺着 54 个文件，加起来约 100 MB。文件名都是系统生成的一串 UUID，比如 `0796d284-5039-4f0a-83f8-0a7a0e397c69.pdf`。

**光看文件名，这 54 个文件和 54 个乱码名字没区别，等于存了个寂寞。**

所以我顺手写了个脚本，把每个 PDF 的首屏文字和元数据提出来，生成一张 UUID 到标题的对照表。表一出来，问题就露了：

| 重复次数 | 情况 |
| --- | --- |
| 10 次 | 同一篇文档 |
| 6 次 | 同一篇文档 |
| 5 次 | 同一篇文档（4 篇都这样） |
| 2 次 | 同一篇文档（7 篇都这样） |
| 1 次 | 只有 2 篇没重复 |

**54 个文件，去重后是 16 篇。** 也就是说同一份东西被反复传进去过最多十次，谁也没发现。

::: details 去重是怎么判断的
把标题标准化（去掉开头序号、去掉 "Microsoft Word - " 前缀、去掉所有非字母数字和汉字、截取前 60 字符）之后做 key 分组。标题提取用的是 PDF 元数据里的 Title 字段，取不到就退回用首屏文字的前 160 字。故意做得粗糙——这里只需要发现"这两份是同一篇"，不需要精确的标题。
:::

这一步让归档从"复制一堆文件"变成了"复制 16 篇 + 一张索引表"。**没有这张表，归档目录里的东西我三个月后一个都认不出来。**

## 数据库：唯一不能重建的，Docker 又起不来

清单里最该保的就是数据库。正常的做法是把它启起来，用 `pg_dump` 导出一份 SQL。

问题是 Docker Desktop 起不来。启动之后进程列表里没有它，命名管道 `\\.\pipe\docker_engine` 也不存在，等了三分钟还是这样。

这时候有两条路：要么继续排查 Docker 为什么起不来，要么换一个不需要 Docker 的办法。

我选了第二条。数据库的数据目录是**直接挂载到宿主机的**（不是 Docker 命名卷），这意味着它的文件就老老实实躺在一个普通目录里。那就直接冷备份——把整个数据目录复制一份，236 MB。

需要的时候，用同一个大版本的镜像把它挂回去就能读：

```bash
# 把冷备份的数据目录挂进容器，就能查询或导出
docker run -d --name db-restore \
  -e POSTGRES_PASSWORD=<当初那个密码> \
  -v "<归档目录>/postgres-raw:/var/lib/postgresql/data" \
  -p 15432:5432 postgres:15-alpine
```

::: warning 大版本必须对上
PostgreSQL 的数据目录跨大版本不兼容。备份的时候是什么版本，恢复就得用什么版本，否则容器会直接拒绝启动。所以备份的时候顺手把镜像 TAG 记下来。
:::

顺带说一句，这条路比 `pg_dump` 其实更省事：不用等 Docker、不用进容器、不用管权限。**冷备份换来的代价只有一个——找不到现成镜像的时候，得自己搭一个环境才能读它。**

## 我一开始的判断 vs 实际是什么

| 环节 | 我一开始的判断 | 实际是什么 |
| --- | --- | --- |
| 卸载要多久 | 十分钟，删目录删镜像 | 九成时间花在删之前的审计和归档上 |
| 相关文件在哪 | 就一个源码目录 | 源码、数据卷、镜像、根目录散落的脚本，还有一个 466 MB 的嵌套副本 |
| 上传文件有多少 | 就是那 54 个 PDF | 去重后只有 16 篇，最多的一份传了 10 次 |
| 数据库怎么保 | 起容器跑 `pg_dump` | Docker 起不来，改成直接冷备份数据目录 |

四个判断里，前两个都是"我以为我知道东西在哪"，实际上并不知道。

## 归档之后长什么样

最后留下的目录是这样，一共约 340 MB：

```
归档目录/
├── README-归档说明.md   ← 留下了什么、为什么、怎么恢复
├── workflows/           ← 工作流的导出文件（最有价值的部分）
├── docs/                ← 踩坑记录、复盘笔记
├── papers/              ← 16 篇去重后的文档 + UUID 对照索引
├── db/postgres-raw/     ← 数据库冷备份
├── code/                ← 自己写的脚本和工具
└── env/                 ← 配置文件（含密钥，另外标注了）
```

有一点值得单独说：**归档说明本身是这套东西里最值钱的一页。**

工作流的导出文件我三个月后还能看懂，但"当初为什么从这一版改到那一版""为什么最后弃用了"这种信息，不写下来就永久丢了。所以我给归档目录写的不是文件清单，是决策记录。

顺便，这也解释了为什么我这次没有直接 `rm -rf`：能重建的东西删掉无所谓，但"为什么"没有备份。

## 一句结论

卸载一个自己搭的服务，难点从来不是删，是**分清哪些东西删了就回不来**。

顺序应该是：先列全相关文件 → 按"能不能重建"分两类 → 把不能重建的归档并验证 → 最后才动手删。

::: details 如果只想记三件事
1. 文件名是 UUID 的上传目录，等于没有名字，删之前一定先建索引。
2. "能不能重建"比"重不重要"好判断。
3. 归档说明要写决策，不要只写文件清单。
:::
